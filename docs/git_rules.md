# Git 협업 및 커밋 규칙

## 사람과 AI
Git 초기화·브랜치 생성/전환·스테이징·커밋·푸시·병합·이력 변경은 사람이 수행한다.
AI는 상태/diff 조회, 개발·검증·기록, 커밋 제목 제안만 수행한다.

## 브랜치
- main: 최종 검증된 제출/배포 버전
- develop: 통합 검증, main으로 PR
- feature/common_setup: 공통 구조·규칙·UI
- feature/home: 홈
- feature/market_analysis: 시장 분석
- feature/product_brochure: 제품소개서
- feature/green_claim: 인증/문구 검수
- feature/promotion_studio: 홍보 콘티
기능 브랜치는 최신 develop에서 사람이 생성하고 develop으로 PR.
공동 담당은 같은 브랜치 동시 수정 금지. 별도 작업 브랜치/범위를 합의.
PM/조장도 동일 절차를 따른다. 승인/병합 담당은 팀 합의 전까지 미정.

## 최초 등록 예외
초기 패키지는 Git 없는 폴더에서 준비할 수 있다. 담당자가 main에 최초 등록하고 develop을 생성·푸시한다.
그 이후 main/develop 직접 커밋 금지. 팀원은 최신 develop에서 기능 브랜치 생성.

## 작업 순서
상태 확인 → 미커밋 작업 안전 정리 → 사람이 최신 develop 반영 → 명세 확인 → 개발 → 검증/개인 기록 → 사람이 선택 스테이징·커밋·푸시 → PR 검토·병합·통합 검증.
충돌은 관련 담당자와 확인한다. 남의 변경 삭제·강제 푸시·이력 삭제 금지.

## 커밋
하나의 작업 목적당 하나의 커밋. 관련 개인 프롬프트·검증 기록 포함.
형식: 유형: 한국어 변경 내용
- feat: 포르투갈어 소개서 PDF 다운로드 추가
- fix: 문구 검수 실패 후 입력이 사라지는 문제 수정
- style: 모바일 콘티 카드 간격 조정
- refactor: 소개서 생성 로직을 서비스 모듈로 분리
- docs: 소개서 프롬프트 비교 결과 기록
- test: 인증 근거 누락 사례 검증 추가
- chore: 공통 환경변수 안내 추가
- data: 검수 기준 문구와 출처 추가
수정/최종/완료/작업함만 적는 제목 금지.

## 커밋 체크
- 본인 기능 브랜치와 본인 변경인지 확인
- 공통/타인 파일 의도치 않은 수정 없는지 확인
- 검증·미검증·명세·개인 기록 갱신
- 키·.env·고객 기밀·실제 사용자 파일·캐시·임시 ZIP 포함 금지
- .env.example(비밀값 없음), requirements.txt, 공개/가상 테스트 자료 포함 가능

## PR 본문
변경 목적, 주요 결과, 실제 검증, 미검증/남은 문제, 개인 기록 링크,
공통 파일/API/환경변수/패키지/데이터 형식 변경 여부.
일반 PR: 기능 → develop. 최종 PR: develop → main.
배포 플랫폼은 미정. 확정 후 배포 설정과 실제 브랜치를 일치시키고 배포 커밋/동작을 별도 검증한다.
